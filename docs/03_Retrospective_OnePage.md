# Written Retrospective — Group 5, FUSE AI-201 Module 6 (Deliverable C, one page)

**Project:** Real-Time Network Intrusion Detection (NSL-KDD → Normal / DoS / Probe / R2L / U2R) — Streamlit prototype + FastAPI alternative, final model HistGradientBoosting (acc 0.80, macro-F1 0.66, weighted-F1 0.78 on held-out KDDTest+, n=22,544).

**Achievements.** We carried one project honestly from proposal (Module 4) through implementation (Module 5) to a demonstrable prototype (Module 6): a single saved pipeline artifact that applies identical preprocessing at train and serve time, a two-tab Streamlit app (single-record form + batch CSV with template, probabilities, latency, and download), a validated FastAPI + Dockerfile deployment path, and a 6/6 whole-system test suite. Evidence-first model selection mattered — the proposed Random Forest was beaten by HistGradientBoosting, so we promoted the winner and documented why. Our strongest habit was honest reporting: the missed macro-F1 ≥0.80 target, the R2L/U2R recall gap (0.28 each), and the staleness of NSL-KDD are stated in the app, report, and video rather than hidden.

**Challenges.** Severe imbalance (52 U2R training rows) plus 17 test-only attack types made rare-class recall the ceiling on every approach; tuning and class-balancing lifted macro-F1 only to 0.665. Historical benchmark features do not cover encrypted, cloud, or modern attack traffic, so every "real-time" claim needed qualification. As an 11-member group we also faced integration overhead — aligning column orders, artifact paths (`models/` vs. app-relative), and Streamlit/FastAPI validation rules across contributors.

**Lessons learned.** (1) Reproducibility is a feature: one pipeline artifact + pinned requirements + a smoke test eliminated most "works on my machine" failures. (2) Baselines first: Majority/Tree/LogReg framed every later gain and made the final comparison credible. (3) UX is safety engineering in security tools — bounds, templates, explicit errors, and a persistent analyst-review disclaimer prevent the most dangerous failure mode: confident misuse. (4) File-based metric logs suffice for a prototype, but promotion decisions need MLflow-style run tracking and time-sliced holdouts, which we specify rather than pretend to operate.

**Limitations.** R2L/U2R recall (~0.28) makes the system unsuitable for autonomous blocking; probabilities are uncalibrated ranking scores; evaluation is on a 1990s-era benchmark, not live traffic; monitoring (drift dashboards, canary, retraining gates) is a written plan, not a running service.

**Planned improvements.** Calibrate probabilities and add confidence-gated triage ("review queue" below 0.60); targeted R2L/U2R data collection + cost-sensitive/threshold tuning; MLflow registry with canary releases; adversarial-robustness review and a pilot on anonymised modern traffic before any operational use. We leave Module 6 with a working, tested, honestly-documented prototype and a realistic path — not a production claim — to something deployable.
